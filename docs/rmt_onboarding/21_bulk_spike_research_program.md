# Семь этапов проверки bulk/spike-топологии RMT

Дата фиксации протокола: 12 августа 2026 года. Сценарий запуска:
`examples/benchmark/rmt_bulk_spike_research_program.py`. Машиночитаемый план:
`docs/experiments/rmt_research_program_plan_20260812/research_program_plan.json`.

## Общий принцип

Программа разделяет реализацию, проверку безопасности и подтверждение
исследовательской гипотезы. Каждый этап пишет данные инкрементально в
собственный каталог. Состояние всей программы хранится в
`research_program_state.json`, а переходы — в
`research_program_events.jsonl`. Повторный запуск пропускает завершённые этапы.

Отрицательный результат Phase S.1 не блокирует программу: в этом случае
сохраняется безопасная равномерная выборка строк. Провал классификационного
критерия, пилота, независимого подтверждения или полной сетки блокирует
зависимые этапы.

## Этапы

| № | Этап | Объём | Решение |
|---:|---|---:|---|
| 1 | Защищённый выбор геометрии для классификации | 480 | Проверить вероятности, сохранение классов и неухудшение A10 относительно A2 |
| 2 | Условный выбор `uniform` или `capped_leverage` | 480 | Разрешить capped leverage только там, где внутренние фолды подтверждают пользу |
| 3 | Реальный bulk/spike-пилот | 320 | Сопоставить B0, B1, B2 и выбранный B3 на четырёх задачах |
| 4 | Независимое подтверждение | 640 | Повторить неизменный протокол на восьми новых задачах |
| 5 | Полная AMLB-сетка | 1200 | Проверить перенос на семь регрессионных и восемь классификационных задач |
| 6 | Плотная бюджетная сетка | 1600 | Оценить качество на десяти бюджетах для восьми репрезентативных задач |
| 7 | Итоговый анализ | 16 кривых | Оценить показатели степени, доверительные интервалы и бюджеты деградации 1%, 3% и 5% |

## Варианты топологии

- `B0_standard_A9`: обычные partition-модели, равномерный выбор строк и
  защищённая геометрия A9/A10;
- `B1_bulk_single_spike`: один широкий bulk expert и один aggregate spike
  expert;
- `B2_bulk_multi_spike`: один bulk expert и несколько spike experts по
  сигнатурам компонент;
- `B3_validation_selected`: выбор B0/B1/B2 только по внутренним фолдам с
  обязательным возвратом к B0 при недостаточной уверенности.

Во всех вариантах совпадают внешний тест, семейство модели и общий уникальный
бюджет строк. Для классификации вероятности выравниваются по глобальному
множеству классов, а восстановление классов выполняется обменом строк без
изменения бюджета.

## Полнообъёмный эталон

Для каждого сочетания `dataset/seed/model` один раз обучается модель на всём
внешнем обучающем разбиении. В него входят внутренние обучающие, калибровочные
и селекторные строки; внешний тест не используется. Эталон переиспользуется
между бюджетами и задаёт:

- абсолютную деградацию ROC AUC;
- относительную деградацию RMSE или log loss;
- время обучения и вывода;
- число деревьев, листьев, разбиений и максимальную глубину LightGBM;
- устойчивость профилей важности признаков и средних абсолютных SHAP-вкладов.

## Закон масштабирования

Для функции потерь используется модель с точным полнообъёмным якорем:

\[
L(b)=L_{\mathrm{full}}+A\left(b^{-\alpha}-1\right),
\qquad 0<b\le 1.
\]

Для ROC AUC функцией потерь считается `1 - ROC AUC`. Параметр `alpha`
показывает скорость ухудшения качества при уменьшении бюджета. Статус
`supported` присваивается только при наличии не менее шести бюджетных точек,
`R^2 >= 0.80` и показателе степени, не лежащем на границе допустимого
интервала. Иначе результат маркируется как разреженный, плохо
аппроксимированный или ограниченный границей.

## Запуск и возобновление

Полный запуск:

```bash
python examples/benchmark/rmt_bulk_spike_research_program.py \
  --output-root /path/to/run_rmt_bulk_spike_program
```

Запуск выбранного этапа вместе с его зависимостями:

```bash
python examples/benchmark/rmt_bulk_spike_research_program.py \
  --output-root /path/to/run_rmt_bulk_spike_program \
  --stages bulk_spike_pilot
```

Этапы 5 и 6 используют одинаковые настройки на общих задачах и бюджетах.
Перед плотной сеткой совместимые записи полной сетки копируются в новый
каталог с `reuse_manifest.json`; пересчитываются только отсутствующие бюджеты.

## Точка повторного запуска

После слияния изменений серверный запуск следует начинать с этапа 1. Этапы 1
и 2 независимы по смыслу, но выполняются последовательно, чтобы не создавать
конкуренцию за вычислительные ресурсы. Переход к этапу 3 разрешён после
завершения обоих и прохождения классификационного критерия безопасности.
